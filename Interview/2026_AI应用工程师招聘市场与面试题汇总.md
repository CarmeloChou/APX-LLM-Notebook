# 二、核心结论

当前“AI 应用工程师”已经不是单纯的大模型算法岗，也不是只会调用模型 API 的开发岗位，而是一个交叉岗位：

```text
软件工程能力
    +
LLM / RAG / Agent 系统能力
    +
数据与后端能力
    +
评估、安全、成本和上线能力
    +
业务理解与产品交付能力
```

企业越来越看重的不是“使用过多少框架”，而是：

1. 能否完成真实业务链路；
2. 能否解释技术选型；
3. 能否识别系统失败模式；
4. 能否通过评估证明系统有效；
5. 能否将 Demo 变成可维护、可观察、可部署的服务。

# 七、LLM 基础高频题与参考答案

## 7.1 Transformer 中 Q、K、V 分别是什么？

**参考答案：**

Self-Attention 让每个 token 从其他 token 中动态聚合相关信息。Q 表示当前位置想寻找什么，K 表示每个位置提供的匹配索引，V 是实际要聚合的内容。

```text
Q = X × Wq
K = X × Wk
V = X × Wv
Attention = softmax((Q × K^T) / sqrt(dk)) × V
```

Q 与 K 的点积衡量相关性，Softmax 将其转换为权重，再对 V 加权求和。除以 `sqrt(dk)` 是为了控制点积尺度，避免 Softmax 过度饱和。

## 7.2 为什么 Decoder-only 模型需要 Causal Mask？

**参考答案：**

自回归语言模型要求第 t 个位置只能根据自己和之前的 token 进行预测。如果训练时看到未来 token，就会发生信息泄漏，训练条件与真实生成条件不一致。Causal Mask 会屏蔽未来位置，使训练和推理保持一致。

## 7.3 Attention、FFN 和残差连接各自做什么？

**参考答案：**

- Attention 负责 token 之间的信息交换；
- FFN 对每个 token 的特征进行非线性变换；
- 残差连接保留原始信息，并改善深层网络中的梯度传播。

现代大模型的大量参数通常位于 FFN，而 Attention 主要决定上下文信息如何流动。

## 7.4 预训练、SFT 和偏好对齐有什么区别？

**参考答案：**

预训练通过 next-token prediction 学习语言分布、通用知识和模式；SFT 通过指令—回答数据让模型学会助手行为、任务格式和指令遵循；DPO、RLHF 等偏好优化进一步使输出符合人类偏好、安全要求和业务目标。

## 7.5 LoRA 为什么有效？

**参考答案：**

LoRA 假设下游任务所需的权重变化具有较低的内在秩。它冻结原始权重，只训练低秩增量：

```text
W_new = W + ΔW
ΔW = B × A
```

因此可以显著降低训练参数量、优化器状态和显存使用。Rank 越大容量越强，但成本和过拟合风险也会提高，并不是越大越好。

## 7.6 LoRA 和 RAG 怎样取舍？

**参考答案：**

LoRA 更适合学习稳定的行为、格式、风格和领域表达；RAG 更适合频繁变化、需要引用和审计的事实知识。实际系统可以二者结合，但不应该把动态业务知识全部依靠微调写入模型参数。

## 7.7 模型为什么会产生幻觉？

**参考答案：**

语言模型优化的是下一个 token 的概率，而不是事实数据库中的一致性。当知识不足、上下文不完整、检索错误或任务歧义时，模型仍可能生成语言上合理但事实错误的内容。

常见缓解措施：

- RAG 和外部数据工具；
- 来源引用；
- 结构化输出；
- 证据验证器；
- 明确拒答条件；
- Human-in-the-loop；
- Bad Case 评测和回流。

# 八、RAG 高频题与参考答案

## 8.1 请讲一下完整的 RAG 流程。

**参考答案：**

离线侧：

```text
文档解析
→ 清洗
→ 结构和元数据提取
→ Chunk
→ Embedding
→ Index
```

在线侧：

```text
Query 理解
→ 改写或分解
→ 稀疏/稠密召回
→ Rerank
→ 上下文构建
→ 带引用生成
→ 评估
```

RAG 的价值是让模型访问可更新、可追溯的外部知识，而不是完全依赖参数记忆。

参考：

- [RAG 原始论文](https://arxiv.org/abs/2005.11401)

## 8.2 Chunk 大小怎样确定？

**参考答案：**

Chunk 没有统一的最优值，应根据文档结构、问题粒度、Embedding 模型和生成上下文共同确定。

- 太小：语义和上下文不完整；
- 太大：噪声增加、匹配不精确、占用更多 token；
- overlap 太大：索引冗余和重复召回。

更可靠的做法是按标题、段落和语义边界切分，再用标注问题集比较不同方案的 Recall@K、Rerank 和最终回答质量。

## 8.3 为什么要做 Hybrid Search？

**参考答案：**

BM25 擅长政策名称、企业名称、编号和专有名词；向量检索擅长语义近似和同义表达。Hybrid Search 可以先分别召回，再通过 RRF 或加权融合候选，最后用 Reranker 精排，因此通常比单一检索更稳。

## 8.4 Reranker 解决什么问题？

**参考答案：**

Embedding 双塔模型将 query 和文档分别编码，适合大规模快速召回，但二者交互较弱。Cross-encoder Reranker 同时输入 query 和候选文档，能够进行更精细的相关性判断，但计算成本较高，所以通常只对初步召回的小规模候选进行精排。

## 8.5 向量召回不准确怎么办？

**参考答案：**

应先定位问题发生在哪一层：

1. 文档解析是否错误；
2. Chunk 是否与问题粒度匹配；
3. Embedding 模型是否适配语言和领域；
4. Query 是否需要改写或分解；
5. Metadata Filter 是否过严或过松；
6. top-k 是否合理；
7. 是否需要 BM25、Rerank 或多路召回。

不能看到召回不准就直接更换向量数据库。

## 8.6 怎样评估 RAG？

**参考答案：**

应分层评估：

- 检索：Recall@K、Precision@K、MRR、NDCG、Hit Rate；
- 重排：相关文档排名提升情况；
- 生成：Faithfulness、完整性、Answer Relevance；
- 引用：Citation Precision、Citation Recall；
- 系统：P95 延迟、成本、空召回率、失败率。

最好结合人工标注、规则指标、LLM Judge 和线上用户反馈，不应只依赖一种评估方式。

## 8.7 RAG 知识库如何不停服更新？

**参考答案：**

可以采用版本化索引或双索引：

```text
旧索引继续服务
→ 后台构建新索引
→ 执行一致性检查
→ 原子切换 alias / version
→ 保留旧索引用于回滚
```

结构化数据还要处理增量更新、删除标记、文档版本、缓存失效和失败补偿。

## 8.8 多个文档的信息冲突怎么办？

**参考答案：**

应保留每条证据的来源、日期、版本和权威等级，不要在检索阶段静默合并。生成阶段应明确展示分歧，优先选择更新且权威的来源；如果冲突会影响高风险决策，应触发人工复核。

# 九、Agent、Tool、Memory 高频题与参考答案

## 9.1 Agent 和 Workflow 有什么区别？

**参考答案：**

Workflow 的路径主要由代码预先定义，强调稳定和可预测；Agent 根据目标和观察结果动态决定下一步，强调适应性。

真实工业系统通常采用：

```text
Workflow 外壳
    +
局部 Agent 决策
```

数据库查询、权限和报告渲染等确定性步骤写在代码中；检索路由、计划调整和信息综合可以交给模型。

## 9.2 ReAct 是什么？

**参考答案：**

ReAct 让模型交替进行推理和行动：

```text
Reason
→ Action
→ Observation
→ Reason
```

行动让模型获取外部信息，观察结果又可以修正计划。优点是灵活；缺点是容易循环、成本较高、长任务可能偏航，所以需要明确预算和停止条件。

参考：

- [ReAct 论文](https://arxiv.org/abs/2210.03629)

## 9.3 Tool 应该怎样设计？

**参考答案：**

一个可靠 Tool 应具备：

- 单一且明确的职责；
- 清晰、不重叠的名称和描述；
- 严格的输入输出 Schema；
- 超时和错误定义；
- 权限和副作用说明；
- 独立测试能力；
- 日志和 Trace。

模型只负责生成调用意图，Runtime 校验参数和权限后才执行真实函数。

## 9.4 Function Calling 的完整流程是什么？

**参考答案：**

```text
用户请求
→ 模型读取 Tool Schema
→ 模型生成工具名和参数
→ Runtime 校验 Schema
→ 权限检查
→ 执行真实函数或 API
→ 标准化 Tool Result
→ 返回模型继续生成
```

真正执行函数的是 Runtime，不是 LLM。

## 9.5 State、Config 和 Memory 有什么区别？

**参考答案：**

- State：当前 Agent Run 中不断变化的业务信息，例如 messages、plan、documents、answer；
- Config：运行环境和身份信息，例如 thread_id、user_id、model、trace_id；
- Memory：跨步骤或跨会话保存，并在需要时取回的信息。

LangGraph Checkpointer 负责保存 thread 级 State；Store 更适合跨 thread 的用户长期信息。

参考：

- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- [LangGraph Memory](https://docs.langchain.com/oss/python/langgraph/add-memory)

## 9.6 为什么会出现历史对话重复？

**参考答案：**

常见原因是：

1. 同时使用自定义 Memory 和 LangGraph Checkpointer；
2. 自定义 Memory 把完整历史重新注入；
3. LangGraph 又根据相同 thread_id 恢复一份历史；
4. 或者把历史拼成一个新的 user message，破坏了对话角色结构。

解决办法是确定短期对话历史的唯一权威来源，并保留 user/assistant 的消息角色，不手工重复拼接完整历史。

## 9.7 LangGraph 的核心价值是什么？

**参考答案：**

LangGraph 是面向有状态 Agent 的 Runtime 和编排框架，主要提供：

- 显式 State；
- Node 和 Conditional Edge；
- Checkpoint 和持久化；
- Interrupt 和恢复；
- Human-in-the-loop；
- 流式事件；
- 长任务容错和调试。

它的价值不是让模型更聪明，而是让多步骤 Agent 的执行过程更可控、可恢复和可观察。

参考：

- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

## 9.8 如何防止 Agent 死循环？

**参考答案：**

组合使用：

- 最大步骤数；
- 时间和 token 预算；
- 重复 Tool Call 检测；
- 重复 Observation 检测；
- 结构化完成条件；
- 失败计数；
- 降级或转人工；
- Trace 回放和 Bad Case 分析。

只设置 `max_steps` 能防止无限执行，但不能解决错误规划的根因。

## 9.9 Tool 执行失败怎么办？

**参考答案：**

首先按照错误类型处理：

| 错误 | 处理方式 |
|---|---|
| 参数错误 | 将明确错误返回模型，重新生成参数 |
| 临时网络错误 | 有限次数退避重试 |
| 权限错误 | 直接终止，不应重试 |
| 空结果 | 重新规划或声明信息不足 |
| 副作用失败 | 检查事务、幂等键和实际执行状态 |
| 连续失败 | 熔断、降级或 Human-in-the-loop |

## 9.10 单 Agent 和多 Agent 如何取舍？

**参考答案：**

任务共享大量上下文、流程不复杂时，应优先使用单 Agent 加多 Skill。只有在子任务可以清晰隔离、需要独立上下文、真正能够并行，或者存在明确专业角色时，才考虑多 Agent。

多 Agent 会增加：

- 通信成本；
- 上下文丢失；
- 状态一致性问题；
- 并发冲突；
- 延迟；
- 调试复杂度。

## 9.11 MCP 和 Function Calling 有什么区别？

**参考答案：**

Function Calling 是模型表达工具调用意图的机制；MCP 是 Host、Client、Server 之间交换工具、资源和上下文的协议。

MCP 解决连接、发现和复用问题，不负责 Agent 的高级规划。

参考：

- [MCP 官方架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

# 十、后端与工程化高频题

## 10.1 为什么 AI 应用后端经常使用 FastAPI 和 async？

**参考答案：**

LLM API、数据库、向量检索和网络搜索都是 I/O 密集操作。异步可以在等待外部服务时处理其他请求，从而提高并发能力。

但是 `async def` 不会自动让阻塞函数变成异步。如果在事件循环里调用同步数据库或同步网络客户端，仍然会阻塞服务。

参考：

- [FastAPI：Concurrency and async / await](https://fastapi.tiangolo.com/async/)

## 10.2 Request Model 和 Agent State 为什么要分开？

**参考答案：**

Request Model 是对外 API 契约，只包含客户端允许提交的字段；Agent State 是内部执行结构，可能包含计划、工具结果、文档、错误和中间状态。

分开以后：

- 内部工作流变化不会迫使 API 跟着变化；
- 客户端不会接触内部状态；
- 输入和输出权限更清晰；
- 测试和版本管理更方便。

## 10.3 Router、Service、Runtime、Repository 如何分工？

**参考答案：**

```text
API Router
    接收 HTTP 请求、校验、返回响应

Service
    编排一次业务动作

Agent Runtime
    执行 Agent 的状态流转和工具决策

Repository
    封装数据库访问

Infrastructure Client
    封装 LLM、Redis、搜索等外部技术实现
```

核心原则是让 HTTP、业务逻辑、Agent 推理和数据库访问互不混杂。

## 10.4 SSE 和 WebSocket 如何选择？

**参考答案：**

SSE 适合服务器单向推送，例如 token、节点状态和报告进度；实现简单，兼容普通 HTTP。WebSocket 适合持续双向通信，例如用户在 Agent 执行中暂停、补充信息或批准操作。

普通聊天流式输出通常优先 SSE；强交互任务再考虑 WebSocket。

## 10.5 缓存应该怎样设计？

**参考答案：**

先区分缓存范围：

- 一次 Agent Run 内避免重复调用：请求级缓存；
- 单机多请求复用：TTL Cache；
- 多实例共享：Redis；
- 相似语义问题复用：语义缓存。

缓存键必须包含所有影响结果的参数、用户隔离信息和数据版本。数据更新后需要有 TTL 或主动失效策略。

## 10.6 数据库 Tool 怎样保证安全？

**参考答案：**

- 使用参数化 SQL；
- 不向模型开放任意写 SQL；
- 最小权限账号；
- 读写工具分离；
- 限制表、字段、结果数量和超时；
- 高风险操作要求人工确认；
- 记录审计日志；
- 写操作使用事务和幂等键。

## 10.7 为什么需要幂等性？

**参考答案：**

Agent 节点可能因为超时、重试或恢复而重复执行。对于支付、发送消息、创建任务等副作用操作，如果没有幂等控制，就可能执行两次。

常用方法是客户端或 Runtime 生成幂等键，服务端保存执行状态，相同幂等键只允许产生一次业务结果。

# 十一、Evaluation、Observability 与安全

## 11.1 怎样评估一个 Agent？

**参考答案：**

不能只看最终答案，应评估完整执行轨迹：

- 任务是否完成；
- Tool 是否选对；
- 参数是否正确；
- 步骤是否多余；
- 是否发生循环；
- 证据是否充分；
- 失败后是否恢复；
- 成本和延迟是否达标。

应建立覆盖真实任务、歧义问题、缺少数据、冲突证据、恶意输入和长任务的 Golden Set。

## 11.2 换模型后怎样确认效果没有回退？

**参考答案：**

首先固定 Prompt、工具、检索结果和评测集，在同样输入下比较：

- 任务成功率；
- 工具选择和参数准确率；
- 结构化输出成功率；
- 引用正确率；
- 延迟和成本；
- 安全拒答行为。

通过离线回归后，再用小流量灰度或 A/B Test 验证线上表现。

## 11.3 线上需要记录哪些内容？

**参考答案：**

- request_id、user_id、session_id、thread_id；
- 模型和 Prompt 版本；
- 每个节点的输入输出摘要；
- Tool 参数、结果、耗时和错误；
- 检索候选与最终证据；
- token、成本和整体延迟；
- 中断、重试和人工审批；
- 最终评估结果。

敏感信息必须脱敏，不能为了 Trace 造成新的隐私泄露。

## 11.4 如何防止 Prompt Injection？

**参考答案：**

- 将网页和文档视为不可信数据；
- 明确区分系统指令和检索内容；
- 不让文档内容决定工具权限；
- 工具使用白名单和最小权限；
- 对 URL、路径和数据库参数做校验；
- 敏感操作需要确认；
- 检测数据外传和越权请求；
- 记录安全审计日志。

## 11.5 怎样降低 Agent 成本和延迟？

**参考答案：**

优先顺序通常是：

1. 减少无意义步骤；
2. 缩短上下文和 Tool 描述；
3. 并行独立的 I/O；
4. 小模型处理分类和路由；
5. 大模型处理复杂综合；
6. 缓存稳定工具结果；
7. 压缩检索上下文；
8. 流式返回；
9. 用 P95 延迟和任务成功率验证效果。

## 13.1 三分钟项目介绍模板

```text
我做的是一个面向产业研究和募投报告的垂直 Agent 系统。

业务上的主要问题是，传统产业研究需要从大量政策、报告、企业和案例资料中人工检索并组织证据，耗时较长，而且结论难以追溯。
```
